# Case: Twin-Instance Recovery from Partial Failure (anonymized v19-b5)

## Context
- Project: K-brand operational data sync (anonymized)
- Strategy instance: requested batch reload of N tabular targets via execution platform
- Execution instance: 6-min server hard limit on synthesis platform

## Trigger
- Execution timeout mid-clear-and-write → 3 of N targets corrupted
- Backup sheets auto-generated by prior trim phase remained intact

## Branch Tree Applied (Block 5)
- A. restore + delete backup — max safety on cell quota, but pre-verify backup loss = irreversible. Rejected.
- **B. restore + retain backup — chosen.** Reversible, marginal cell cost.
- C. wrapper-by-file — covers only sub-scope X, sibling-domain gap remains. Partial fix.
- D. full re-run, sheet-by-sheet — 6min × N round-trips, time-prohibitive.
- E. accept loss — zero learning value, counts as CCPE failure case.

Strategy instance chose B — non-irreversible until post-verify, retains rollback capacity.

## Safety Guards Triggered (Block 6)
- Destructive write blocked by execution-side classifier on first attempt
- Strategy instance re-issued with `deleteBackupAfter:false` flag
- Post-restore inspect-verify mandatory before any backup cleanup

## Lessons
- Long server-side ops + clear-then-write = corruption risk → **split into ≤6min units**
- Always retain backup until post-verify (`deleteBackupAfter:false` default)
- Auto-classifier blocking destructive ops is a feature, not a bug — it forced the strategy instance into the safer B branch
- Twin-instance pairing surfaces failure modes a solo session would silently absorb
- recoveryTime prediction missed by 1 round-trip — single-roundtrip assumption is brittle when verify is mandatory
- cell quota recovery exceeded prediction by 2× — cleanup compound effect (backup deletion + maxRow/Col trim) under-modeled
- Empirical pairing efficacy: strategy instance maintained context across timeout while execution instance handled retries; sole-session recovery would have lost the branch-tree state
